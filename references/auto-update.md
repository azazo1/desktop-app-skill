# 桌面应用自动更新机制 (客户端侧)

本文只覆盖应用内部的更新实现, 与具体语言和 GUI 框架无关. 发布侧 (CI 打包, 产物命名, SHA256SUMS 生成, tag 流程) 由 create-github-release-flow skill 保证, 本文不重复; 实现更新功能时需与其产物契约对齐.

推荐将更新实现为独立模块, 按职责分四层:

- 更新运行时: 状态机, 启动静默检查, 设置持久化.
- 发布查询: latest release 查询, 版本比较, 平台资产匹配.
- 下载校验: SHA256SUMS 解析, 流式下载与校验.
- 安装: 平台安装策略, 安装器整包落地, 重启与备份清理.

## 状态机

`Idle -> Checking -> (UpToDate | Available | Failed)`, `Available -> Downloading -> (ReadyToRestart | Failed)`, `ReadyToRestart -> (HandedOff | DmgOpened)`; 这两个后继状态都必须由用户点击后进入: 安装版走 `HandedOff`, 无论 windows, linux 还是 macos, 都是把落地工作交给脱离进程的安装器或替换脚本; 只有 macos 便携运行走 `DmgOpened`. Downloading 可被用户取消, 取消后终止下载任务回到 Available, `.part` 保留供下次续传.

- 更新状态集中存放并加锁, UI 读取不可变快照渲染; 检查, 下载, 安装在后台任务中执行, 状态变化后通知 UI 刷新. 取消下载时安全终止后台任务, 不得让半途的写入损坏已完成的 `.part` 校验语义.
- `Failed` 携带用户可读的错误信息; 手动检查失败记 warn, 静默检查失败只记 debug, 不打扰用户.
- 下载完成只到 `ReadyToRestart`, 绝不自动交接或自动退出: 替换, 重启这些动作必须由用户点击 "重启并更新" 类按钮触发, 点击之前应用保持正常运行 (托盘驻留, 后台服务继续跑, 窗口可正常开关). "下载完就静默交接重启" 或 "下载完自动退出" 都属于不符合规范.
- `HandedOff` 表示用户在点击后把落地工作交给了脱离本进程的安装器或替换脚本 (windows 的 `-setup.exe`, linux 的 `install.sh`, macos 的 bundle 替换脚本), 应用必须尽快走统一退出路径退出, 不能继续驻留 (见 "安装策略"). 该状态只可能由用户点击产生, 不能由下载完成产生.

## 检查更新

- 检查接口: `https://api.github.com/repos/<owner>/<repo>/releases/latest`, 请求头 `Accept: application/vnd.github+json`. 该接口自动排除 draft 与 prerelease.
- HTTP 403 与 429 识别为 GitHub API rate limit, 给出明确错误信息.
- 版本比较: 当前显示版本与候选 tag 都按运行时版本号约定归一化 (strip 可选 `v` 前缀, 截断 `-<commit>` 与 `^<commit>` 后缀) 后解析 semver, 候选严格大于当前版本才提示; 同版本视为不更新, 覆盖本地带 commit 后缀重构建的场景.
- `dev-build` 等无法解析出 semver 的构建永远不提示更新, 保证开发构建安静.

## HTTP 客户端与系统代理

- 更新涉及的全部对外请求 (release 查询, SHA256SUMS 与更新包下载, 系统通知等) 都必须走系统代理, 尊重用户当前的代理设置, 不允许绕过代理直连.
- Rust + reqwest 不需要自己读系统设置再拼 `reqwest::Proxy`: 默认开启的 `system-proxy` feature 已经按平台读系统代理 (macOS 走 SCDynamicStore 读系统偏好设置, windows 读注册表 Internet Settings, 其余平台读环境变量). 只有显式调用 `.proxy()` 或 `.no_proxy()` 才会关掉这个自动行为, 需要自定义代理时要意识到这一点.
- 系统代理只在构建 client 的那一刻读取一次, 所以不能在启动时建一个长期存活的 client 全程复用: 每次检查更新与每次下载都在请求前重新构建 client, 让运行期用户改代理, 开关 VPN, 切换网络之后立刻生效.
- client 构建封装成一个统一入口函数, 调用点不各自拼装, 避免有的请求走代理有的不走; 其他栈按其原生方式读取系统代理 (Electron 用 `session.resolveProxy`).
- 探测不到代理时退化为直连; 代理不可用, 握手失败或超时要在日志里记 warn 并给出用户可读错误, 不静默失败. 静默检查仍按规则只记 debug.
- 同一次下载流程内 (含断点续传的后续请求) 复用本次构建的 client, 但不要把 client 跨请求长期缓存, 否则代理变更不生效.

## 检查时机

- 启动静默检查: 启动后延迟 5 秒执行一次, 仅当自动检查开启时执行; 该设置默认开启, 以 `update.auto_check` 为键持久化, 更新窗口开关与托盘勾选项双向同步.
- 静默检查发现新版本且该版本未被用户跳过时, 发系统通知引导到主界面; 网络失败只记日志.
- 手动检查入口: 托盘菜单 "检查更新" (触发检查并打开更新窗口), 更新窗口内 "重新检查".

## 资产匹配与下载校验

- 客户端按精确文件名匹配 release 资产: `<app>-<tag>-<platform>-<arch>[-<variant>].<ext>`, 变体段与扩展名由平台和分发形态共同决定; 同一 release 必须存在 `SHA256SUMS` 资产. 匹配不到直接报错.
- 默认形态 (安装版) 的匹配目标: windows `-setup.exe`, linux `-setup.tar.gz`, macos `.dmg`. 项目明确提供便携版时, 便携形态改匹配 windows `-portable.zip`, linux `-portable.tar.gz`, macos 便携运行仍用 `.dmg`. 不做跨变体降级匹配.
- 分发形态由构建期注入的常量给出 (与构建版本同一注入路径), 首次启动时再用运行期位置复核一次, 两者不一致时按便携运行处理并记 warn: windows 要求可执行文件位于 `%LOCALAPPDATA%\Programs\<App>` 且 HKCU 卸载项存在, linux 要求位于 `$HOME/.local/opt/<app>/` 且安装标记存在, macos 要求位于 `<bundle>/Contents/MacOS/`.
- fake 测试构建 (见 SKILL.md 的 fake-dist 章节) 仅版本号为 `v0.0.0`, 更新检测, 资产匹配与安装流程和正式应用完全一致.
- 先下载 SHA256SUMS, 按安装包文件名提取期望摘要; 解析容忍 `*` 二进制标记与 CRLF 行尾, 缺少对应行时报错.
- 更新包下载到 `<data_dir>/update/<name>.part`, 支持断点续传: 启动下载时若已存在 `.part`, 携带 `Range: bytes=<已下载字节数>-` 请求续传, 服务器返回 206 则追加写入; 返回 200 (对方不支持 Range), `.part` 大小不小于 total 或本地文件异常时, 丢弃 `.part` 从头下载. 每个数据块触发进度回调 (received 与 total, total 来自 Content-Length, 可能为 None).
- 下载完成后对整个 `.part` 计算 sha256 (续传后增量哈希状态不可复用, 统一整文件计算), 摘要大小写不敏感比对, 不匹配则删除 `.part` 并报错; 匹配后 rename 为正式文件名落盘.
- 落盘即下载流程的终点: 只把状态切到 `ReadyToRestart` 并通知 UI, 不触发任何安装, 替换或退出动作, 后续动作全部由用户在 UI 上发起 (见 "状态机" 与 "安装策略").

## 安装策略 (平台差异)

- 统一前提: 下载完成只表示 "安装包已就绪", 什么时候替换与重启由用户决定. 用户点击 "重启并更新" 之前不得做任何不可回退的替换动作, 也不得自行退出进程; 用户可以继续用当前版本干活, 也可以直接退出应用.
- 用户下载完却先退出 (或长时间不点重启) 时, 安装包保留在 `<data_dir>/update/` 下; 下次启动或下次检查更新时, 若本地安装包存在且 SHA256SUMS 校验通过且版本仍匹配, 直接回到 `ReadyToRestart` 并提示, 避免让用户重复下载整个包.
- 安装版一律由安装器落地: 应用只负责把新版安装器交接出去, 由安装器整目录替换程序文件, 因此新版新增的 dll 与资源会被补齐, 新版移除的文件会被清理. 各平台的差别只在交接对象 (windows 的 `-setup.exe`, linux 的 `install.sh`, macos 的替换脚本), 不需要为它们各写一套逐文件替换逻辑.
- 交接前先写 pending 标记 (见 "安装结果回显"), 交接后应用立刻进入退出中状态并走统一退出路径: 停止后台服务, 刷盘日志, 释放单实例锁. 退出中状态下窗口关闭必须按真退出处理, 不再隐藏到托盘, 否则安装器发出的关闭请求会被当成隐藏, 替换无法完成.
- 每次启动时清理上次更新遗留的备份 (windows / linux 便携版的 `<exe>.old`, linux 安装版的 `.<app>.old`, macos 的 bundle 备份) 与残留挂载点, 文件被占用则静默留待下次; 更新日志与结果文件保留.

### windows 安装版: 交接给 Inno Setup 安装器

- 形态前提判断: 当前可执行文件确实位于 `%LOCALAPPDATA%\Programs\<App>` 且 HKCU 下存在对应卸载项时才按安装版交接; 否则说明它是被搬到别处运行的副本, 退回按便携运行处理并记 warn.
- 交接命令: `setup.exe /SP- /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /CLOSEAPPLICATIONS /LOG="<data_dir>\update\apply-update.log"`, 以脱离进程的方式 spawn, 不等待它结束, 也不要带出控制台窗口. `/SP-` 不能省: `/VERYSILENT` 不会去掉安装器开头的确认提示. 不要传 `/FORCECLOSEAPPLICATIONS`, `/RESTARTAPPLICATIONS` 和 `/DIR`.
- 安装器由项目打包脚本用 `iscc` 编译: `[Files]` 中应用私有文件带 `ignoreversion` 保证覆盖安装; `[InstallDelete]` 清理上一版本留下而本版本不再提供的私有产物; `[Run]` 的 postinstall 项 (`Flags: nowait`, 不加 `skipifsilent`) 负责安装完成后重新拉起应用; `RestartApplications` 设为 `no`, 避免 Restart Manager 与 `[Run]` 双重拉起.
- 旧进程还没退净时由 Restart Manager 兜底 (`CloseApplications` 默认 yes, 静默模式下会自动关闭占用待更新文件的进程). 不要依赖 `AppMutex` 的交互确认, 它在静默升级下不能作为流程保证.
- 失败线索以 `/LOG=` 指定的日志为准: 安装器回滚后应用可能没有被重新拉起, 由下次启动的 pending 判定把结果呈现给用户 (见 "安装结果回显").
- 卸载由 Inno 生成的卸载器完成, 卸载项 DisplayVersion 随版本更新; 卸载不得删除用户数据目录.
- windows 的 release 构建是 GUI 子系统, 没有控制台, 全程错误必须落到日志与 UI, 不能依赖标准错误输出.

### linux 安装版: 交接给脱离进程的 install.sh

- 形态前提判断: 当前可执行文件位于 `$HOME/.local/opt/<app>/` 且 `install.sh` 落盘的安装标记存在时才按安装版交接; 否则退回按便携运行处理并记 warn.
- 交接步骤: 把 `-setup.tar.gz` 解到 `<data_dir>/update/staging-<version>/`, 校验解包结果确实含 `install.sh` 与 `payload/`; 用 `setsid` 以脱离进程方式启动 `install.sh --silent --wait-pid <app_pid> --prefix "$HOME/.local" --log "<data_dir>/update/apply-update.log" --result-file "<data_dir>/update/apply-update-result.txt"`, 子进程的 stdout 与 stderr 追加到同一日志; 启动成功后应用走统一退出路径.
- `install.sh` 的执行顺序: 等 `<app_pid>` 消失 (超过约 60 秒视为失败, 写结果文件后退出) -> 把 `payload/` 复制到目标父目录内的 `~/.local/opt/.<app>.staging-<version>` (必须与目标同卷, 最后一步 rename 才不会跨卷) -> 旧目录改名为 `.<app>.old` 让位 -> 暂存目录 rename 就位 -> 刷新 `~/.local/bin/<app>` 链接, desktop 项与图标 -> 删除备份 -> 用 `setsid` 重新拉起应用.
- 整目录交换才是升级的正确形态: 上一版本有而本版本没有的文件随旧目录一起消失, 不要退化成逐文件覆盖.
- 失败与回滚: 任一步失败都要把已让位的备份移回并把暂存目录删掉, 把可读原因写进 `apply-update-result.txt`, 然后重新拉起旧版本; 参数或路径自检这类 "什么都还没做" 的失败不得顺带删除或移动任何路径.
- 卸载走 `install.sh --uninstall`: 删除安装目录, `~/.local/bin` 链接, desktop 项与图标, 保留用户数据; 检测到应用仍在运行 (pid 或单实例锁) 时拒绝卸载并提示先退出.
- linux 允许 rename 含运行中可执行文件的目录, 所以交接不需要 windows 那种逐文件让位技巧; 但也不要趁应用还在运行时提前交换目录, 以免运行中的进程引用到半新半旧的文件树.

### macos: 交接给脱离进程的替换脚本

产物是 dmg, 而进程存活时 LaunchServices 会占用已安装的 `.app`, 直接覆盖会被系统拒绝, 也不能像 windows 安装器那样在进程外覆盖安装目录, 所以采用的方式是: 下载完成进入 `ReadyToRestart` 并等待用户, 用户点击 "重启并更新" 后应用才把替换工作写成一个脚本并立即启动它, 自己随即退出; 脚本等旧进程消失后完成挂载, 替换与重新拉起. 下载完成本身不触发交接, 点击之前应用照常驻留运行.

- 形态前提判断: 只有当前可执行文件确实位于 `<bundle>/Contents/MacOS/<exe>` 结构内才交接替换, 否则视为便携运行 (直接跑二进制, 没有可替换的 bundle), 退回打开 dmg 的手动引导 (`DmgOpened`). 这一步与替换脚本的启动同在用户点击之后执行, 下载完成不得自动打开 dmg 或自动挂载镜像.
- 脚本由应用生成并落盘到数据目录的 `update/` 下 (如 `apply-update.sh`), 赋予可执行权限后以脱离进程 (detached) 的方式 spawn, 保证它不随父进程退出而死; 脚本自身再忽略 SIGHUP. 脚本内容通过参数占位符注入路径, 注入前必须做 shell 单引号转义, 避免带空格或引号的路径破坏脚本.
- 子进程的 stdout 与 stderr 必须追加重定向到 `update/apply-update.log`, 不能丢弃: `hdiutil`, `ditto`, `mv` 这些外部命令的报错是排查替换失败的唯一线索, 只留一句自己写的失败文案等于没有线索. 脚本内对每个可能失败的外部命令做同样的重定向, 并让命令行抛出的原因能落进日志.
- 启动脚本后立刻返回 `HandedOff` 状态 (触发条件只能是用户点击 "重启并更新", 见上), UI 显示 "正在退出并替换, 请勿手动关闭进程" 一类的提示, 应用随即走统一退出路径: 停止后台服务, 刷盘日志, 释放单实例锁. 交接后不应再做任何需要用户等待的交互.
- 被替换的实体是 bundle 本身, 不是它所在的目录: 暂存路径必须是 bundle 的同级隐藏条目 (如 `/Applications/.Pinote.app.update-0.6.0`), 备份必须是 bundle 自己的 `<bundle>.app.old`. 传递路径时统一以 bundle 为基准推导同级条目, 不要拿 bundle 的父目录 (即 `/Applications`) 再向上取一层, 那样暂存会落到根卷而必然失败, 备份更会变成 "把整个应用目录改名后删除". 脚本在任何破坏性操作之前先自检这两个路径确实与 bundle 同级, 不满足就中止并落盘原因.
- 脚本执行顺序: 轮询等待旧 PID 消失 (超过约 60 秒视为放弃, 此时不打开 dmg, 因为应用还活着拖拽同样会被拒), 校验暂存与备份路径形状, 确认目标 bundle 所在目录可写, 挂载 dmg 并从中定位 `.app`, 用 `ditto` 把新 bundle 复制到 bundle 同目录的暂存路径 (同卷才能保证最后一步 rename 不跨卷), 清除 `com.apple.quarantine` 隔离属性避免替换后首次启动被 Gatekeeper 拦截, 旧 bundle 改名为 `<name>.app.old` 让位, 暂存目录 rename 就位, 删除备份, 最后重新拉起应用.
- 回滚与失败落盘: 任一步失败都要回滚 (新 bundle 就位失败时把备份移回), 并把可读原因写入 `update/apply-update-result.txt`, 然后立刻 `open` 旧 bundle 把应用重新拉起; 结果文件如何回显给用户见 "安装结果回显". 回滚只撤销确实执行过的动作 (用标志位记录是否已改名让位, 路径是否已通过校验), 路径校验失败这类 "什么都还没做" 的失败绝不能顺带去删除或移动任何路径.
- 脚本日志写入 `update/apply-update.log`, 替换完成后保留日志便于排查; 应用每次启动清理上次遗留的 bundle 备份, 替换脚本与残留挂载点目录 (`mount-*`), 但保留日志.
- 失败提示要区分两类: 旧进程未按时退出时应用仍在运行, 提示用户稍后重新发起更新; 目标目录不可写, 挂载失败, 镜像中没有 `.app` 或复制失败时旧进程已退出, 此时提示手动拖拽安装 (不会再被占用阻挡).
- 重新拉起应用依赖单实例锁已经释放, 因此退出路径必须真正释放锁, 或锁本身带 pid 存活检测.
- 验证要求: 这条分支只有在应用确实以 `.app` 安装到真实位置 (如 `/Applications`) 时才走到, 便携构建与 fake 构建都不覆盖它, 所以最容易被漏测. 单元测试要断言暂存与备份路径确实由 bundle 推导得出, 而不是把写好的正确路径直接喂给脚本生成器来自证; 此外还要在真实安装位置用真实 dmg 完整跑一次替换, 确认两个路径落在 bundle 同级, 且同级其他条目与挂载点都没有被波及.

### 便携版 (可选形态): 替换自身可执行文件

仅在用户明确要求提供便携版时才实现这条路径: 形态常量取便携值, 资产匹配走便携版变体, 落地方式为解包归档并替换自身可执行文件. 载荷必须是单文件自包含可执行形态 (见 SKILL.md 的分发形态章节), 出现 dll, so 或资源文件的载荷用这条路径无法整体升级.

- 运行中的二进制允许 rename 不允许覆盖删除: 先把当前可执行文件 rename 成 `<exe>.old` 让位, 再把新二进制 move 到原路径; 中途失败把 `.old` 移回来回滚, 保证应用始终可用.
- rename 因跨文件系统失败时, 退回复制后删除源文件.
- unix 下设置 0o755 可执行权限.
- 替换动作在用户点击 "重启并更新" 时才执行 (下载完成不预先替换二进制): 点击后以新二进制启动新进程接管, 当前进程随后走正常退出路径. 重启前先释放单实例锁, 或锁采用 pid 存活检测, 避免新进程在旧进程退出前抢锁失败而直接退出.
- 每次启动时清理上次更新遗留的 `.old` 备份, 文件被占用则静默留待下次.

## 安装结果回显

- 交接任何安装器或脚本之前, 先在 `<data_dir>/update/apply-update.pending` 写下这次交接: 目标版本, 分发形态, 安装包文件名, 交接时间与日志路径. 这个标记是判断 "更新到底落地了没有" 的唯一依据, 不能省.
- 下次启动时若 pending 存在:
  - 当前版本已达到或超过目标版本, 说明落地成功: 删除 pending, 在更新窗口与状态栏提示 "已更新到 vX".
  - 当前版本没变, 说明安装器没跑完或没把应用拉起来: 读取 `apply-update-result.txt` (linux 安装脚本与 macos 替换脚本会写) 或 `apply-update.log` 的末尾摘要 (windows 安装器的 `/LOG=`), 在更新窗口展示可读原因与重试入口, 然后删除 pending.
- 结果展示一直保留到用户下一次主动检查更新. 日志与已下载的安装包都保留: 安装包留在 `<data_dir>/update/` 供下次直接回到 `ReadyToRestart`, 日志是排查落地失败的唯一线索, 不要清理.

## 验证要求

- windows 安装版: 必须在真实安装位置完整跑一次升级, 不能只做单元测试. 先装 v1, 再触发更新到 "比 v1 多一个 dll 的 v2", 断言新 dll 已就位, v1 有而 v2 没有的文件已消失, 卸载项的 DisplayVersion 变成 v2, 用户数据目录内容未被改动, 且应用被重新拉起.
- linux 安装版: 以 `--prefix` 指向临时目录跑一遍安装与升级, 断言整目录交换后新增文件存在, 被移除的文件消失, `~/.local/bin` 链接与 desktop 项的 Exec 指向新目录, `.<app>.old` 备份与暂存目录都已清理; 另外覆盖一次失败回滚, 确认旧版本仍可运行且结果文件里写入了可读原因.
- 便携版 (仅在项目提供该形态时): 断言替换后磁盘上的可执行文件确为新版本, `.old` 备份已清理.
- 三平台都要覆盖一次 "交接后应用退出, 安装器完成落地并重新拉起应用" 的完整链路, 以及一次安装器失败时靠 pending 回显原因的分支.

## UI 与托盘集成

- 状态栏: 无更新时显示当前版本号; Available / ReadyToRestart / HandedOff / DmgOpened 状态时替换为加粗链接, 引导打开更新窗口.
- 更新窗口: 当前版本; 各状态对应文案与控件; release notes 滚动区; 下载进度条与已下载字节数; 操作按钮 "立即更新", "取消更新" (仅 Downloading 状态显示, 取消后回到 Available 可再次发起), "跳过此版本" (以 `update.skipped_version` 为键持久化, 静默检查不再提示该版本), "查看 Release 页" 外链, "重启并更新", 失败信息与重试. "重启并更新" 旁必须说明它会运行安装程序并退出当前进程, 交接期间不要手动关闭进程. 下载进行中关闭更新窗口不中断下载, 重新打开仍可见进度. HandedOff 状态下不再提供任何操作按钮, 只显示 "正在退出并运行安装程序, 请勿手动关闭进程" 一类的提示与进度指示.
- `ReadyToRestart` 是等待用户决策的状态, 不是自动执行的过渡态: 窗口显示 "新版本已下载, 重启后生效" 与 "重启并更新" 按钮, 并说明当前版本可正常继续使用, 由用户决定何时点击. 不得在此状态自动关闭窗口, 自动重启或自动退出进程; 关闭更新窗口后该状态与按钮在状态栏入口重新打开时依然可见.
- 重启按钮的落地方式按平台与形态不同 (安装版交给平台安装器, 即 windows 的 `-setup.exe`, linux 的 `install.sh` 与 macos 的替换脚本; 可选便携版替换自身可执行文件), 但对用户呈现的语义一致: 点了才换, 不点不换.
- 托盘菜单: "检查更新" 项 + "启动时自动检查更新" 勾选项.
